# monet v2：nitro 功能面对标 + hooks 深化

## Context

v1 轨道（monet-rn plan M0–M6）已完成：四端矩阵绿（模拟器/真机 × iOS/Android）、DESIGN.md 验证 IOU 清零、全部边界记录在案。v2 的范围就是那些"v1 明确不做"与"hooks v1 边界"的存量，加上工程收尾。本 plan 入库即 W0。

**范围定调（2026-11-10，用户确认）**：

- **permessage-deflate：永久非目标**。v1 双侧不支持、一致性绊线已钉（`unrequested_deflate_offer_round_trips`，见 2026-11-10 提交）；启用压缩需要 iOS 手写帧实现 deflate（维护成本不值得）且跨实现分帧风险高。绊线保留——它存在的意义恰是"不支持"这个契约本身：tungstenite 上游哪天实现了 RFC 6455 §4.1 第 5 步，检查先红，两端一起收紧，但**不**因此启用压缩。
- **monet-ws 换纯同步 tungstenite：不做**。私有单线程 runtime 藏得干净（调用方零 tokio 感知），无动机。
- monet-dart（flutter_rust_bridge）独立轨道，不在此 plan（core 不动原则下互不影响）。

## 已核实的关键事实（决定设计形状，2026-11-10）

1. **iOS 的 per-request 参数只差 core 层**：`UrlsessionTransport` 的 `follow_redirects`/`timeout_ms` 是实例级 builder 字段，但 Swift 控制面 `transport_start(id, url, method, followRedirects, timeoutMs)` **已按调用传参**——W1 只需要 core `Request` 的覆盖语义 + execute 读取优先级，Swift 侧零改动。
2. **Android 上传已是流式接口**：`MonetUploadProvider extends UploadDataProvider`（Cronet 的流式上传契约），现为字节数组适配器。流式上传 = provider 增量喂入 + 控制面加 body-chunk 命令，接口形态不变。
3. **core 的流式上传 Rust 侧已验证**：`body::channel` + conformance 的 `slow_upload_does_not_block_new_requests` 检查（M3 起）就是流式请求体——缺的只是 TS 层入口与 iOS Swift 数据面。
4. **背压的自然落点已存在**：monet-rn 的 fetch pump 是"信号 + 零拷贝拉取"（on_chunk 信号 + take_chunk 拉取）——拉取本身就是消费侧节奏；缺的是"JS 未取走时暂停 transport 读取"的阀门。iOS 数据面有原生原语：`URLSessionTask.suspend()/resume()`。
5. **mock 响应需要 trait 变体**（hooks plan 已记录）：request hook 是 Request→Request，造不出 Response。
6. **token refresh 的 shape 已存在**：M5 电池 `http:hook_retry_uses_new_token` 就是完整 token-refresh 场景（401 → response hook 刷新 → retry 出口 → 新 token 放行）。A2/W4 的第一步是评估"hook 组合子 vs 内置策略"，很可能结论是已有等价能力 + 文档对齐。

## 工作流

### W1：per-request timeout / redirect（core Request 加宽，地基项）

- **core**：`Request` 加 per-request 覆盖字段（`timeout_ms: Option<u64>`、`follow_redirects: Option<bool>`），builder 方法 `with_timeout_ms` / `with_redirect_policy`；`Client::execute` 的读取优先级：request 覆盖 > client/transport 默认。
- **transport 传透**：urlsession 直接可用（事实 1）；rustls 的 head 超时与 redirect 逻辑从 request 读；httpengine 的 Cronet 侧 per-request redirect（`setRedirectBehavior`）与 timeout（`UrlRequest.Builder` 的 timeout 参数）核实后接。
- **monet-rn**：`fetch(url, {timeoutMs, redirect})` 透传进 FetchOptions；TS 类型加宽。
- **电池**：conformance 加 per-request 覆盖检查（client 级 500ms + request 覆盖 100ms → 按 100ms 失败；client 级 follow + request no-follow → 3xx 原样返回）；JS 电池镜像。

### W2：通道层一体设计——上传流式 + 响应背压（设计记录，2026-11-10）

同一个 pump 的两个方向。设计定稿如下：

**上行（流式上传）——API 面**：

- TS：`fetch(url, {body: AsyncIterable<Uint8Array | ArrayBuffer | string>, ...})`。Hermes 原生支持 async iteration（ReadableStream 在 RN 无标准实现，不接）；string/ArrayBuffer 形态照旧。
- core 零改动：`Body` 本来就是流（channel），rustls 侧现状即流式（hyper 逐块拉取，`slow_upload` 检查自 M3 起在跑）。
- monet-rn pump：AsyncIterable body → 建 channel body + 馈给任务（JS chunk → `feed.send_chunk`；耗尽 → `complete`；异常 → `error`），与 head race 并行。
- **分片跟进（独立落地，落地前文档标注"该平台上传为缓冲实现"——语义正确，内存上不流式）**：
  - iOS：`needNewBodyStream` 桥——Swift 合成 InputStream，Rust 通道喂给（`uploadTask(withStreamedRequest:)` 形态替换 `httpBody`）。
  - Android：`MonetUploadProvider` 从字节数组适配器改为增量队列（`getLength()` 未知长度路径核实）。

**下行（响应背压）——水位语义**：

- **契约不变，行为有界**：v1 的"信号 + 零拷贝拉取"已是对话式消费（与 nitro `Promise<bool>` 的"逐块确认"节奏等价）——**响应侧零 API 变化**。变化在内部：pending 队列有界，慢消费者传导为网络读取暂停。
- **水位**：每在途 fetch 的 pending 界 = **4 块**（泵侧块通常 16–64KB，界约 256KB）。高水位暂停（pending ≥ 4），低水位恢复（pending ≤ 2）——滞回防抖动。
- **transport 暂停原语**（各得其所）：
  - rustls：泵在 pending 满时不 poll `body.next()`——hyper 流控沿链路传导（TCP 窗口收缩）。**无需 transport 改动**（core 通道的天然界）。
  - urlsession：`URLSessionTask.suspend()/resume()`（数据面原生原语；suspend 后 data 事件停止交付）。
  - httpengine：`issue_read` 门控——`on_read_completed` 后仅当队列有余量才发起下一读（读循环节奏本就在桥里，天然落点；Cronet 内部缓冲停止读网络）。
- **与 cancel 的交互**：`task.cancel()` 对 suspended task 照常生效（suspend 只停交付不改生命周期，`didCompleteWithError` -999 照发——iOS 文档行为）；httpengine 门控期间走 armed native cancel；rustls 的 race_cancel 不受 poll 门控影响。
- **电池观察面（JS 侧即可钉住契约）**：慢消费者（每块 sleep）期间，信号数 − 取块数 ≤ 界 + 1（JS 可断言）；服务器侧 TCP 读窗口停滞为可选增强，不做。

**分片与验证顺序**（每片独立提交）：

- **W2a**：TS AsyncIterable + pump 馈给 + JS `http:streaming_upload` 电池（慢喂 + 并发不阻塞，镜像 Rust `slow_upload`）。**已实施（2026-11-10）**：`fetch_stream/chunk/complete/error` 四方法（通道发送半存 FetchRegistry，JS 线程同步喂给）；泵重构为共享 `spawn_fetch_pump`（`PumpBody::Buffered|Stream`——**流式遇 response-hook retry 显式失败**：流已消费不可重放，v1 靠缓冲才能重试）；TS `body: AsyncIterable<string | ArrayBuffer>` 自动走流式路径。已知边界：馈给为无界通道（生产者节奏 App 自控，有界化列后续）；iOS/Android 栈 `buffer_body` 收集整个流（语义正确，W2c/d 补真流式）。iOS 模拟器 22/22 + TLS 6/6 验证（含 streaming_upload）；Android 模拟器从零构建复验 22/22 + TLS 6/6（`fetch_stream`/`configure_trust` 符号级确认无缓存）。TLS 电池在 Android 的前置：adb reverse 8964-8967（`localhost` 基址 + pin 键拒 IP 的必然结果；反向集随设备重启失效——server bin 启动横幅已打印该命令）。
- **W2b**：下行背压——泵界 + 三 transport 阀门 + JS `http:slow_consumer_bounded` 电池（全平台同语义）。**已实施（2026-11-10）**，一个 plan 假设被推翻后按实况落地：
  - **core**：v1 的 body 通道是**无界**的（"同步回调不阻塞"的刻意决策）——"rustls 无需 transport 改动"不成立，三栈都要真阀门。新增 `body::bounded(cap)`（`BoundedBodySender`：`send().await` 等容量 = 异步馈给者的自然暂停点；`try_send() -> Delivery{Sent|Full(Bytes)|Closed}` = 同步探针；abort 走 slot——满缓冲时错误不能排队，EOF 时浮出，不丢语义）。有效容量 cap+1（futures-channel 语义：越界的那条仍入队再停靠发送者）。请求侧（上传）维持无界（W2a 已定）。
  - **泵界（monet-rn）**：FetchState 队列带水位——高 4（暂停拉取）低 2（take_chunk 唤醒泵，滞回防抖）；`wait_for_capacity` 与 cancel race（满队列 + abort 不得等永不来的 take）；cleanup 唤醒停靠的泵（观察 state 移除）。
  - **rustls 阀门**：响应通道换 `bounded(4)`，`pump_body` 改 awaited send（与 cancel race）——hyper 流控沿链路传导（HTTP 窗口 → TCP）。
  - **httpengine 阀门**：`on_read_completed` → `try_send`，Full 则**不再 issue_read**（溢出块至多 1 个，读停在门上）；body watcher（既有 parked-thread）扩展为三路循环（wake 通道 + cancel + 终结）：drain 溢出（awaited send，消费者节奏）→ 恢复读（`ResumeRead` 闭包，`start_request` 同步 helper 里 arm——**在 async 块里直接构造 `vm.scope` HRTB 闭包会破坏 future 的 Send（"not general enough" over JObject lifetime）**，与 W1 把 engine 的 duplicate_global 挪出块外同因）；**terminal 暂存制**：on_done/on_error 先 stage（首个 terminal 胜出——Cronet 在 onSucceeded 后的杂音错误不覆盖）再由 watcher 排空后 apply——**终结对满缓冲不能插队**，且 cancel 后 watcher 不退出（terminal 异步到达，apply 是它的活）。
  - **urlsession 阀门**：`on_chunk` 返回暂停信号 → Swift `task.suspend()`（只停交付不改生命周期，iOS 文档行为）；watcher drain 后经新控制面 `transport_resume`（trampoline + `@_expose` Swift）恢复。terminal 暂存制同 httpengine。
  - **电池**：服务器新增 `/backpressure`（24×4KB、10ms 间隔，对 60ms 消费者 6:1 失配）；JS 检查走原生协议观测——信号数 − 取块数 = 队列深，全程 ≤ 5；字节精确（98304，门后不丢）；门确曾挂上（max depth ≥ 2）。**注意 transport 会合并服务器块**（Cronet 读回调 24 块 → 14 信号）——断言按字节不按信号数（第一版按 ≥20 信号断言在真机上翻车）。
  - 验证中揪出并修掉两个问题：① 检查初版按"≥20 信号"断言——**transport 会合并服务器块**（Cronet 读回调 24 块 → 14 信号），改字节精确（98304）+ max depth ≥ 2；② iOS `cancel_after_head_aborts_body` 回归——**泵停在 body.next() 里观测不到 cancel**，abort 全靠 transport 拆 body 传递，而 iOS 上 suspended task 的 cancel 交付时序让 on_done 抢先（terminal first-wins 吃掉 Cancelled）。修法双管齐下：泵的 body 拉取也 race cancel（abort 不再依赖 transport 拆除）+ watcher 观测到 cancel 后不再 resume（避免和 terminal 赛跑）。suspended task 上 task.cancel() 的 didComplete 时序假设由此降级为"不依赖"——泵层保证语义。
  - 验证：双端模拟器 **23/23**（Android API 35 httpengine：slow_consumer_bounded 978ms、cancel_after_head 10ms；iOS 26.5 urlsession：slow_consumer_bounded 1030ms、cancel_after_head 9ms——suspend/resume 阀门 + 终结暂存全部经真电池）。rustls 阀门由 core 单测（等容量/满探针/abort-slot）+ host conformance 承载——它是 <34 fallback，任何电池 rig 都不会以它为 fetch 栈跑端到端，记录在案。另：iOS xcodebuild 的产物落 DerivedData（非 ios/build/）——安装要用 DerivedData 路径；Rust 符号在 MonetDemo.debug.dylib 里（主二进制只有 58KB，nm 主二进制查符号会误判"旧包"）。
  - 已知边界：上传馈给仍无界（W2a 遗留，生产者自控节奏）；服务器侧 TCP 窗口停滞观测未做（plan 原定的可选增强，不做）。W2a 所记"iOS/Android 栈 buffer_body 收集整个流"已由 W2c/W2d 全部闭合。
  - **遗留问题（2026-11-11 深挖后 CLOSED）——iOS `slow_consumer_bounded` 挂死**：约 1/3 轮次超时（20s）；**task 的 didComplete 从不触发**（os_log 无 Task-finished 行）——任务被挂起后再未恢复，completion 停止投递，JS 消费者饿死。连接层 ~290ms 就完成（见下：代理解耦了服务器节奏）。**证据**（Rust 侧文件日志，非侵入观测）：失败轮呈现合并块背靠背双 stall（24KB+12KB）→ 修复前 4 次 suspend 对 3 次 resume——**URLSessionTask 的 suspend/resume 是计数语义**，未配对的 suspend 永久挂起任务。**已落地两道加固**（都修掉了观测到的真实失衡，host 全绿）：① **episode 语义**（registry）：`stalled` 标志 = 一集 stall 从开启（首个 Full 的 chunk）到 watcher 排空恢复；集中段内到达的 chunk 只进 overflow、**不再要求第二次 suspend**——一集一挂一恢复；② **Swift 侧 `valveSuspended` 门控 + `still_stalled` 复查**（TransportShim 锁内）：resume 只在真挂起过时执行，drain 完成先清标志后发 resume + 两端同锁串行——消灭 resume 先于 suspend 的乱序对（快排空场景 suspend 被跳过、resume 也跳过，配平为零）。**但 episode 版仍复现过一次 run 1 挂死**——根因未完全闭环。**环境因素**：宿主系统代理（127.0.0.1:7890）开启时 app 的 localhost:8964 流量走 lo0 proxy——代理读穿整个响应（连接 ~290ms 完成），阀门 suspend 无法传导到服务器侧，压力模式与 W2b 验证时（代理状态未知）不同。**下一步**：(1) 关系统代理复验（隔离环境因子）；(2) 带 Rust 阀门文件日志抓 episode 版挂死轮——若 watcher 显示所有 episode 都关闭、resume 都发出、仍无 terminal，则卡点在 URLSession 的 suspend 语义本身，阀门需换设计（iOS dataTask 无 issue_read 式读门控——候选：放弃 task.suspend，改为 JS 侧更高水位的有界缓冲，或每请求专用 URLSession 的 delegate 队列控制）。**方法论教训**：截图读数不可靠（本次发现两帧画面曾被读成五段进度，"23/23" 系误读）——电池结果一律走 **AX 树/uiautomator 文本抽取**（os_log/NSLog 看 Swift、app 容器文件日志看 Rust）；仪器会扰动竞态（NSLog 拓宽 didReceive 尾部窗口），**Rust watcher 侧文件日志是不扰动 delegate 路径的观测通道**（带它复现过挂死）。
  - **2026-11-11 深挖记录**（本轮会话，仪器化 + 三轮重构）：
    - **复现率变化**：旧 valve 代码（W2b 时代 vendor 回退态）0/12；d38208d+计数修复 4/10；**彻底移除 valve 后 12/12 确定性挂死**——valve 实际在掩盖问题，移除后得到可靠复现。
    - **计数配平证据**：watcher 文件日志（`MONET_VALVE_LOG=1` launch 参数或环境变量开门，写 app 容器 `$HOME/monet-valve.log`——stderr 在 iOS 不可捕获、NSLog 扰动 delegate 竞态、文件日志是唯一非侵入通道）显示挂死轮的 suspend/resume **完全配平**（count 1→0 每集）——根因不在 valve 配对，在 **URLSessionTask 本身**：resume 后任务永远不再投递数据与 didComplete。
    - **valve 移除**（按本节预案执行）：`on_chunk` 不再返回暂停信号（溢出块 + watcher 排空的纯 Rust 节奏控制；Swift 侧 suspend/resume/计数全删；`transport_resume`/`valve_count`/`still_stalled` 桥面全删）。**代价**：iOS 无网络级暂停（Cronet 的 issue_read 门控、rustls 的通道容量都做不到 URLSession 上）——峰值内存 = 响应大小 + 缓冲，记为 iOS 边界。
    - **当前确定性复现的形态**：W2c 流式上传 fetch 之后的**所有后续 fetch**（含 slow_consumer 的）——pump 启动 ✓、探针 ✓、但 **body watcher 不再记录任何 terminal**、无 stall 日志——怀疑共享 session 的 delegate 状态被 UploadPipe 扰动或 watcher 线程生命周期中断。下一步：给 on_response_head / watcher spawn / stage_terminal 加日志定位停摆环节。
    - **streaming_upload iOS 假失败已修**：其一又是 vendor 回退（上午的构建编了 W2b 时代旧代码，W2c 不在包里——**vendor 回退第三次咬人**，crates/ 改动后必须 sync）；其二是平台边界——CFNetwork 会缓冲小体流并带 Content-Length 发送（探针走 live、wire 报 length，同请求实证）——chunked 断言改为 Android-only，iOS 记边界。
    - **方法论沉淀**：电池结果经服务器 `/report` 路由回传（服务器 stdout 即 rig 日志，替代不可靠的截图读数）；`/upload` 路由打印 wire 头（len/te/body_bytes）；uiautomator/AX 读数保留为备用。

- **W2d**：Android provider 增量队列。**已实施（2026-11-10）**，`getLength()` 契约先核实（plan 原定第一步）：**返回 -1 = chunked 上传**（"size not known in advance"，官方支持；"not all servers support chunked" 由 conformance 的 hyper 承载）；`read()` 允许**异步完成**（"either synchronous or asynchronous"——停靠 sink 稍后回调）；流不可重放 → `rewind` 走 `onRewindError`（文档明示这是合法路径）——与泵的"流式遇 hook retry 显式失败"同一语义，HTTP 307/308 body-preserving redirect 在流式上传上会失败，记录在案。
  - **wire 形态决策**：`Body::take_complete()`（core 新增，noop-waker 探针不停靠）——已完成的 body 照旧缓冲（Content-Length + 可 rewind），活流走 chunked provider。探针把"顺手拉到的字节"随 `Live { drained }` 交回（通道无 peek），feeder 先喂 drained 再拉流。竞态无害化：JS 生产者若在探针前就完成整个流，退化为缓冲上传（字节等价，仅 wire 形态不同）。
  - **upload.rs**（httpengine，纯 Rust 可 host 测试）：无界队列 + `Take{Wrote/End/Failed/Empty/Gone}` + `NotifyProvider` 闭包（jni.rs 供给，同 CancelNative 形状）+ feeder（body watcher 的 parked-thread 模式，三路 race：body.next / cancel / close 通道）。队列无界是 W2a 决定的延伸（JS→Rust 馈给本就无界，Rust 侧设界只界住本地副本，不界流占用）；Cronet 的 read 拉取才是真节奏。
  - **时序钉死**：notify 在 setup 的 vm.scope 内、`request.start()` **之前** arm——provider 一启动就可能 read()，空队列 read 停靠后只有该 notify 能唤醒；feeder 在 setup 成功后 spawn（此时 notify 必已 armed）。close 的权威来源是 Cronet 对 provider 的 `close()`（setup 失败路径也调）；`close_tx` 显式 send + 状态移除双重结束 feeder。
  - **Java（两 embedder 各一份机械拷贝）**：`MonetStreamedProvider`——`getLength()=-1`，read→`takeUploadChunk(id, buffer, pos, remaining)` 直写 direct buffer（无中转拷贝），-1 停靠（存 sink+buffer，`onDataAvailable` 从 feeder 线经 JNI 唤醒）；空 chunk 在 push 时丢弃（0 字节 take 会误读为 End）。**`onRewindError`/`onReadError` 都要 Exception 参数**（API 35 实测，文档页没写清）。桥类新增 `takeUploadChunk`/`closeUpload` 两个 external——RegisterNatives 表扩到 8 项，**两个 embedder 不声明就 init 失败**。
  - **观察面**：`/upload` 响应加 `x-upload-mode: length|chunked`（hyper 消费 transfer-encoding，content-length 的有无即判据）；App.tsx `streaming_upload` 断言双向——慢喂流为 **chunked**（iOS 门控已随 W2c 落地翻转为无条件）、完整 body 恒为 length。curl 双探针先行验证。

### W4：prefetch + token refresh 评估（nitro 源码核实于 /Volumes/YYP_PSSD/OpenSource/react-native-nitro-fetch，2026-11-12）

- **token refresh 评估（结论：组合子已覆盖，零代码）**。nitro 的实现是**声明式配置 + 工具函数**，不是核心 fetch 路径里的自动拦截器：`registerTokenRefresh({target, url, mappings…})` 把端点描述（jsonPath → header 映射、组合模板）存进加密存储，`callRefreshEndpoint(config)` 供手动调用；核心 fetch 路径里**没有 401 触发器**（fetch-core 无 refresh 钩连；配置的消费者是 WS 重连与冷启动 prefetcher）。逐项对照 monet 的 M5 组合子：
  | 维度 | nitro | monet（M5 组合子） |
  |---|---|---|
  | 刷新触发 | 无核心内置（WS/冷启动侧消费配置） | response hook 任意谓词（401/自定义头/任意状态） |
  | 刷新逻辑 | 静态端点 + jsonPath 映射 | 任意 JS（电池 `hook_retry_uses_new_token` 演示完整 shape） |
  | 并发共享 | 存储头缓存（主要服务 WS） | 共享 store + request hook 读取，天然共享 |
  | 失败传播 | `onFailure: 'skip' \| 'useStoredHeaders'` | hook 自决（失败 fetch / 旧 token 重试 / 任意） |
  | WS | 显式 `target: 'websocket'` | WS upgrade 走同一 request hook 链（`ws:request_hook_headers` 证明） |
  结论：**组合子严格覆盖且更灵活**；nitro 的声明式配置只是简单场景的便利面。不做内置策略；文档示例即组合子本体（电池检查即是）。
- **prefetch（形态已定：完整响应缓存，非连接预热）**。nitro 语义（`HybridNitroFetchClient.prefetchStatic` + `FetchCache`）：
  - `prefetch(input, {prefetchKey})`：要求 `prefetchKey` 头；**真实发请求**，完整响应（status/headers/body）存入内存 FetchCache（键 = prefetchKey）
  - **去重**：`beginPending` 原子占位——并发同键 prefetch 只发一次；**在途加入**——fetch 遇到 pending 可 `joinPending` 等同一个请求
  - fetch 侧命中：带同键 `prefetchKey` 头的 fetch 先查缓存——新鲜（TTL，**默认 5s**）→ 立即返回并附加 `nitroPrefetched: true` 头；pending → 加入等待
  - `clearPrefetchCache()`；`prefetchCacheTtlMs` per-request；`prefetchOnAppStart`（注册持久化到加密存储，冷启动由 AutoPrefetcher 原生重取——**依赖存储面，v2 不做**，记录为 v2.2 候选）
  - **已实施（2026-11-12）**。`prefetch.rs`（模块级 FetchCache：key → Pending(waiters) | Done{response, stored_at}；`begin` 原子占位防并发同键、`take_if_fresh` 读时 TTL（nitro 语义——**读取方**的 prefetchTtlMs，默认 5s）、`join` 在途加入、`clear`）；`Monet::prefetch(options, on_done, on_error)`——独立任务跑请求 hook 链（auth 注入）+ transport，终局缓冲 body 入缓存（hook mock/veto → 不留条目）；fetch 侧检查点在泵的 Modified 臂（transport 之前）：新鲜 → `mark_prefetched` 合成 Response（`x-monet-prefetched: true` + extensions 保留）走 mock 臂同路交付；pending → join；miss/失效 → 正常网络（fetch 侧只读不回填，nitro 同款）。TS：`prefetch(input, init?)` / `clearPrefetch()` / fetch init 的 `prefetchKey`/`prefetchTtlMs`（键不上线）。电池 +3：`prefetch_hit`（命中零流量——/request-count 语义修正：**每次读含自身 +1**，干净轮 delta = prefetch 本身 + 末次读）、`prefetch_ttl_expiry`（读侧 1ms TTL → 过期回落网络、无命中标记）、`prefetch_pending_join`（/slow-head 500ms 在途加入，服务器只见一次请求）。验证：iOS 模拟器 **28/28 × 3 轮**、Android 模拟器 **28/28** 零崩溃。顺带修了 W3a 遗留的两处 TS 类型摩擦（resolveRequestHook 的 `mocked: null` 必填字段、mocked body 的 `?? null`）。rig 教训：昨天起的服务器进程还是 W3a 前的二进制——`/request-count` 路由在但计数器从不递增，电池结果前先确认 rig 自身是新的。
  - **原设计记录**：`prefetch(url, {prefetchKey, ttlMs?})` 走真实 fetch 泵，终局把 Response（status/headers/body 缓冲）存入模块级 FetchCache（key → (response, expires_at, pending)）；`fetch` 带 `prefetchKey`（RequestInit 选项）→ 泵在 hook 链后查缓存：新鲜 → **mock 臂交付**（零 transport、零连接）+ `x-monet-prefetched: true`；pending → await 同一 in-flight future；过期/未命中 → 正常走网络（**并回填？否——nitro 不回填，fetch 侧只读**）。`clearPrefetch()` 清全部。**实现约一天**：FetchCache（TTL + pending-join）+ prefetch 入口 + 泵的缓存检查点 + TS 面 + 电池（prefetch 后 fetch 命中/零服务器流量（复用 `/request-count`）、TTL 过期回落网络、pending-join）。
