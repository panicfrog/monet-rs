# monet-rn M5：JS Hook / Observer 设计记录

日期：2026-11-08。状态：已实施（monet-core observer 机制 + monet-rn hook 通道 + TS 层 + 电池 8 项检查，双平台 18/18）。

## 动机

设计目标 #2：给 fetch（和 WS 连接）加上 JS 侧拦截点。典型场景：

- **认证注入**：request hook `await` 一个共享 token store（过期先刷新）→ 加 `Authorization`——nitro `tokenRefresh` 的形状，但跑在 native 管线里
- **环境/灰度**：改写 URL
- **请求 deny-list**：命中即掐（请求不出网）
- **埋点/可观测**：记录每个出站请求与响应头
- **401 拦截 + 刷新重试**：response hook 看见 401 → 单飞刷新 → 要求重跑（调用点保持干净的 `fetch()`）

## 两类拦截点（核心区分）

| | Observer（只读） | Hook（读写） |
|---|---|---|
| 语义 | 看，不影响管线 | 可改写、可中止、可 retry，管线等待 |
| TS 返回 | `void`（类型上改不了） | 显式返回新值 / `{retry: true}` / throw |
| 机制 | TurboCallback fire-and-forget（零延迟，管线不等待） | pending-map + oneshot 回程协议 |
| 时序 | 固定：所有 hook 之后（看到**最终形态**——req 上 wire 前 / res 交给 app 前） | 注册序 |
| 归类规则 | deny-list 归 hook（改变控制流即"写"） | |
| 审查姿态 | 业务放心自加 | 需要过目：数量少、语义重 |

**性能不对称**是设计要点：可观测（最高频用途）走 observer 零延迟；只有真正的读写才付 JS 往返。

## 管线位置

```
fetch:
  cancel 快速失败（既有）
  → request hooks（注册序，每 hook 等待 resolve，与 cancel race）
  → request observers（最终形态，fire-and-forget）
  → transport
  → response hooks（head 到达时、body 继续流，与 cancel race）
  → response observers（最终 head，fire-and-forget）
  → on_head 交付 JS        ← hook 可改写 head；延迟 = hooks 时长（语义即此）
  → body 流（hook 不触碰，透传）

ws_connect:
  → request hooks + observers（upgrade 请求，与 cancel race；无 response hook/retry
    —— upgrade 没有 JS 可见的 head）
  → transport.connect
```

## 回程协议（读写 hook）

TurboCallback 是 fire-and-forget（无返回通道），而 hook 必须把改写结果还回来：

```
① pump 分配 hookCallId → pending[id] = oneshot::channel()
② on_request.call({hookCallId, attempt, url, method, headers}) → JS（JS 线程）
   pump: race(await oneshot, cancel.cancelled())
③ JS hook（可 async）→ resolve_request_hook(id, {url, method, headers})
                      / reject_request_hook(id, {kind, message})
   response 侧另有 retry_response_hook(id)
④ resolve → pump 醒来：改写合入（body/extensions 原样保留）→ 继续
   reject → Error::Hook（kind 已通到 JS 的 ErrorEvent）
   abort → cancel race 赢 → Cancelled；pending 条目由 clear_hooks 或后续 resolve 清理
```

- **无超时**（v1 决策）：不 resolve 的 hook 挂住 fetch，靠 abort 解——超时值是拍脑袋，abort 语义已存在
- **body 不进协议**（v1 决策）：hook 只见 `{url, method, headers}`；core 的 trait 按值传递本就支持 body 改写（Rust 原生 hook），将来 JS 协议加宽 `body?: ArrayBuffer` 是纯加法
- 事件 payload 复用：observer 收到同一 struct（`hookCallId: 0`，无意义）

## retry（response hook 第三出口）

**驱动场景**：10 个并发请求、一个 401 → 预见后续全部失效 → 第一个触发刷新后，其余必须等同一个刷新（单飞）再重试，否则并发刷新会在旋转式 refresh token 的后端互相作废。

```
resolve {retry: true}（TS 联合类型返回，已定）
  → pump 从原始请求重跑完整链（request hooks → transport）
  → request hooks 重跑时 await 同一个共享刷新 promise → 自然注入新 token
```

- **重跑从 JS 输入重建**（FetchOptions + body bytes）——`Body` 是流不可 clone；v1 上传全缓冲，bytes 在 pump 手里
- payload 带 `attempt`（0 起，经 `Extensions` 传递——pump 插、适配器读）；hook 自行放弃；pump 兜硬上限 **3**
- cancel token 跨 attempt 存活
- **单飞在 app 侧**（共享 promise，~10 行）：所有 hook await 同一个；这是"不依赖后台符合最佳实践"的客户端防线
- retry 出口在协议里是 `Error::Body("monet-rn: hook retry")` 哨兵（core 的链把 hook 失败包成 `Error::Hook`，pump 从中识别）——集中在 pump 一处匹配

## API 面

```ts
// monet-rn 导出
addRequestObserver((req: MonetHookRequest) => void)
addResponseObserver((res: MonetHookResponse) => void)
addRequestHook((req: MonetHookRequest) => Promise<MonetHookRequest> | MonetHookRequest)
addResponseHook((res: MonetHookResponse, attempt: number) =>
  Promise<MonetHookResponse | {retry: true}> | MonetHookResponse | {retry: true})
clearHooks()   // 清全部四类 + pending（与 clearPins 对称）
```

resolve 舞步全部在 TS 包装层（hooks.ts）：用户写普通的（可 async）纯函数，`hookCallId` 不外露。

Rust 原生层：同一 core 链（`RequestHook`/`ResponseHook`/`RequestObserver`/`ResponseObserver` traits），monet-dart/host 消费者不经 JS。静态规则层（Rust 实现 + JS 只传配置，零往返）本里程碑不做——有实际用例再加。

## 关键实现决策

1. **hook 链存模块级**（`Monet.hooks: RwLock<HookRegistry>`），不在 Client 上——`rebuild()`（pin 变更）整体换 Client，hook 注册是 app 生命周期状态必须存活。执行侧：read guard 下 clone（`HookRegistry` 浅 clone，Vec of Arc）后**立即放锁**再 await（std guard 非 Send，不能跨 await）。
2. **observer 发射点定死在 core 的 `run_request_hooks`/`run_response_hooks` 末尾**——"最终形态"语义对 Client 用户（execute_with_cancel）自动生效。
3. **取消传播在 pump 侧 race**（不动 core 的 execute_with_cancel）：`race(hooks 链, cancel.cancelled())`；适配器只 await oneshot——pump 丢弃 future 时 sender 悬空，后续 resolve 落空清理。
4. **attempt 经 `Extensions`**（core 的 typed per-request store，正是为此设计）：pump 每 attempt 插 `HookAttempt(n)`，适配器读出来进事件。
5. **WS 复用 request hook 链**：`ws_connect` 的 upgrade Request 前 `race(run_request_hooks, cancel)`——认证头注入用同一套注册，管线免费复用。
6. hook 闭包被 native 持有 = 模块级强注册，活 app 一生（与 M4 的 socket 生命周期问题无关）。

## 电池检查（8 项）

每项 try/finally `clearHooks()`（全局注册，检查串行防污染）：

| 检查 | 断言 |
|---|---|
| `http:observer_zero_impact` | hook 加头 + observer 记录 → fetch 正常完成 且 observer 事件含 hook 加的头（最终形态 + 零影响） |
| `http:request_hook_rewrites_header` | hook 加 `x-hook` → /echo 反射 |
| `http:hook_error_fails_fetch` | hook throw → MonetError kind `Hook` |
| `http:hook_async_resolution` | hook await 50ms 再改 → 头到位（证 pending-map） |
| `http:hook_retry_uses_new_token` | 共享 token（token1）→ 401 → response hook 置 token2 + `{retry:true}` → /auth-guard 200，attempt==0 处触发 |
| `http:hook_retry_gives_up` | 恒 `{retry:true}` → 硬上限后失败（非挂死） |
| `http:abort_during_hook` | hook 永不 resolve；100ms 后 abort → kind `Cancelled` |
| `ws:request_hook_headers` | hook 加 `x-ws-hook` → /hook-echo 首消息 = 头值 |

服务端配套：`/auth-guard`（401 + `x-retry` 响应头 / `Bearer token2` 放行）、`/hook-echo`（upgrade 头回显为首消息）。

## v1 边界（记录在案）

- **Mock 响应**：request hook 是 Request→Request，造不出 Response（需要 trait 变体，将来议）
- **Body 改写/查看**（JS 侧）：协议不含 body（加宽是纯加法）
- **流式 body 检查**：observer/hook 只见 head
- **自动重试之外的重试策略**（5xx 退避等）：retry 出口通用，但策略是 hook 自己写
- **hook 超时**：无（abort 语义已存在）
- **WS retry / response hook**：无（upgrade 语义没有 JS 可见的 head）
